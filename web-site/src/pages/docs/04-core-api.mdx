# 4. Component View: ASP.NET Core Gateway

The **Core API Gateway** is the central nervous system of **ExamGuardian**. Built with ASP.NET Core 9 and Entity Framework Core, it follows Clean Architecture and Domain-Driven Design (DDD) principles. It is responsible for authorization, session lifecycle management, video chunk indexing, AI webhook ingestion, and real-time SignalR WebSocket dispatching.

## 4.2 REST API Endpoints

| Method | Endpoint | Auth | Description |
| :-- | :-- | :-- | :-- |

### Exam Sessions

| Method | Endpoint | Auth | Description |
| :-- | :-- | :-- | :-- |
| `GET` | `/api/examsessions` | — | List all sessions |
| `GET` | `/api/examsessions/{id}` | — | Get session by integer ID |
| `GET` | `/api/examsessions/by-student/{studentId}` | — | Sessions for a student (GUID) |
| `GET` | `/api/examsessions/by-exam/{examId}` | — | Sessions for an exam |
| `POST` | `/api/examsessions/start` | `[Student]` | Start a new session |
| `PATCH` | `/api/examsessions/{id}/finish` | `[Student]` | Finish session and submit score |

**Start Session:**
```json
// POST /api/examsessions/start
{ "examId": 1, "studentId": "3fa85f64-5717-4562-b3fc-2c963f66afa6" }

// 201 Created
{ "id": 42, "examId": 1, "studentId": "...", "startTime": "2026-10-14T10:00:00Z", "isFinished": false, "score": 0 }
```

**Finish Session:**
```http
PATCH /api/examsessions/42/finish?score=85.0
→ 200 OK: updated session with endTime & score
```

### Exam Submission

The actual exam submission is decoupled — the **Qt client** calls `POST /api/Exams/{id}/submit` with answers. Score is calculated server-side:

```json
// POST /api/Exams/{examId}/submit  [Student]
{
  "sessionId": 42,
  "answers": [
    { "questionId": 1, "selectedOptionIndex": 2 },
    { "questionId": 2, "selectedOptionIndex": 0 }
  ]
}

// 200 OK
{ "sessionId": 42, "score": 85.0, "isFinished": true }
```

## 4.3 Examination Session Lifecycle

The examination session follows a simplified two-state lifecycle driven by `IsFinished: bool`:

<Mermaid source={"stateDiagram-v2\n    [*] --> Active: POST /api/examsessions/start\\n(Student Connects & Passes Checks)\n    Active --> Finished: PATCH /api/examsessions/{id}/finish\\n(Student Submits Answers or Time Expires)\n    Active --> Finished: Proctor action via Angular Monitor\n    Finished --> [*]\n\n    note right of Active\n        IsFinished = false\n        Violations accumulate\n        Video chunks upload continuously\n        AI inference running\n    end note\n\n    note right of Finished\n        IsFinished = true\n        Score persisted\n        EndTime stamped\n        Final chunk flushed\n    end note"} />

> **Note:** The session entity uses a boolean `IsFinished` flag. The richer state machine (`Scheduled / InProgress / TerminatedByProctor / Cancelled`) is enforced at the **application layer** in `ExamSessionService` with guard checks that throw `InvalidOperationException` on illegal transitions (e.g., finishing an already-finished session).

### Integrity Scoring Engine

The final Academic Integrity Score is calculated from the accumulated `ViolationAlert` records:

```text
Integrity Score = max(0, 100 - SUM(weight_i × confidence_i))
```

Violation weights by severity category:

| Severity | Examples | Penalty Weight |
| :-- | :-- | :-- |
| **Critical** | Smartphone detected, second person in frame, micro-earpiece, VM detected | 25 |
| **Warning** | Sustained gaze deviation (\|yaw\| > 0.19 or pitch > 0.17), whispering, late-closed prohibited app | 8 |
| **Info** | Brief face occlusion, low-light warning | 2 |

## 4.5 Shared development and production API

Both profiles compile the same Core API. They differ in deployment settings, storage and reload behavior. The API has no development admission signer or development routes. Every attempt requires the ordinary bound identity admission and follows the same authority, deadline, scoring and evidence rules.

The Qt development menu only changes local restriction gates. Core does not manufacture test attempts or seed sample students/exams. Existing migration history is preserved, and a forward migration removes retired test-policy columns.

## 4.6 Absolute examination window

An exam closes at `scheduledStartTime + durationMinutes`. Core rejects start/resume outside that window and sets every attempt deadline to its scheduled end, rather than giving each arrival a fresh duration. Answers received at or after the deadline are rejected; deadline grading uses previously saved answers.

Creation accepts either an explicit UTC/offset timestamp or `scheduledStartLocal` with `timeZoneId`. Core converts local time independently of the browser timezone and rejects DST ambiguity. Catalog DTOs provide `scheduledEndTime`, `serverTimeUtc` and the display timezone.
