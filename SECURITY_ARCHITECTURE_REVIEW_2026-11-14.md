# Безопасность и расширяемость ExamGuardian

Дата: 14 ноября 2026. Проверена текущая рабочая копия, включая незакоммиченные изменения. Прикладной код и конфигурация развёртывания в рамках этого аудита не изменялись.

## Вывод

**JWT есть и реально проверяется. HTTPS предусмотрен, но не обязателен во всех клиентах и вариантах запуска. Авторизация реализована частично: попытки ограничены владельцем, а справочник студентов и выдача их паролей — преимущественно ролью преподавателя.**

Основу стоит сохранить: модульный ASP.NET Core, отдельный процесс Inference, Qt для студента, Angular для преподавателя. Расширяемость улучшать через явные контракты, выделение ответственности и ограничение полномочий. Разбивать Core на множество сетевых сервисов сейчас не требуется.

## Приоритетные изменения безопасности

Приоритет P1: до открытого многопользовательского запуска. P2: следующий этап усиления и роста. Подтверждённый взлом или анонимное выполнение кода в самом приложении этим аудитом не установлены.

### S1. Обязательный HTTPS для production Qt — P1

Файлы: `Client/src/network/client_config.h`, `Client/src/viewmodels/exam_viewmodel.cpp`, `Client/src/network/auth_service.cpp`.

`configureServer()` разрешает `http`, адрес может также прийти из окружения/QSettings. Логин отправляет пароль на выбранный адрес без отдельной проверки защищённой схемы. Перенаправление Nginx не защищает первый HTTP-запрос, уже содержащий пароль.

Предложение: централизованная проверка origin перед любым запросом; production разрешает HTTPS, явно ограниченное исключение для loopback доступно только DEV. Проверять все источники адреса, запретить downgrade/перенос авторизации на другой origin. В проверенных исходниках не найдено отключения TLS-проверки через `ignoreSslErrors`/`VerifyNone` — это сохранить. Certificate pinning не вводить без продуманной ротации сертификатов.

Критерий: production-клиент отклоняет внешний HTTP до отправки пароля; просроченный, недоверенный или чужой сертификат не принимается.

### S2. Разделить ключи и доверие Core/Inference — P1

Файлы: `compose.base.yml`, `Inference/api/auth.py`, `Core/Core/Security/AttemptTokens.cs`, `Core/Core/Security/MediaLinkSigner.cs`.

Core и Inference получают один симметричный JWT secret. Этот же ключ используется Core для attempt/evidence-токенов и подписи медиассылок. Компрометация AI-процесса, обрабатывающего недоверенные медиа, поэтому затрагивает полномочия выпуска пользовательских токенов.

Предложение: access JWT подписывает только Core приватным ключом, Inference проверяет публичным; отдельный ключ допуска AI с узким audience; отдельный ключ медиассылок; `kid` и перекрывающаяся ротация. AI → Core получает узкую сервисную идентичность вместо универсального пользовательского секрета. Не менять все токены одновременно без периода совместимости. Разделение MAC и публичной подписи рассматривает [OWASP JWT Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/JSON_Web_Token_Cheat_Sheet.html).

Критерий: ключи, доступные Inference, не позволяют создать access JWT преподавателя или подписать произвольную ссылку на запись.

### S3. Права преподавателя на студентов и пароли — P1

Файлы: `Core/Core/Controllers/StudentsController.cs`, `Core/Core/Controllers/GroupCredentialsController.cs`, `Core/Core/Exports/GroupCredentialsService.cs`.

Сервис экспорта выбирает студентов по строке группы, не получает пользователя для проверки его прав. GET PDF может включать ранее выданные восстанавливаемые пароли. Это функциональная возможность с чрезмерно широкой ролью, а не просто проблема UI.

Предложение: роли SchoolAdmin/Examiner с назначением групп; отдельные права на справочник, фото, выпуск и повторное получение паролей; аудит таких действий. Для нескольких школ — `SchoolId` и проверка принадлежности на всех ресурсах, включая экспорт и изображения. Для одной школы достаточно назначений групп без преждевременного внедрения полного multi-tenant SaaS.

Критерий: второй преподаватель без назначения не читает фото/пароли и не меняет студента чужой группы; одинаковое имя группы в двух школах не смешивает данные.

### S4. Жизненный цикл сессии входа — P1

Файлы: `Core/BusinessLogicLayer/Services/AuthService.cs`, `Core/Core/Controllers/AuthController.cs`, `monitor/src/app/services/auth.service.ts`.

Access TTL по умолчанию сутки. Refresh хранится непосредственно в User, без истории семейства и атомарного потребления. Параллельная ротация не имеет явной защиты от повторного использования. Выход не отзывает access; при уже истёкшем access авторизованный logout может вообще не выполнить отзыв refresh. В Angular токен хранится в localStorage, доступном исполняемому JavaScript.

Предложение: короткий access TTL, например 10–15 минут после проверки фонового refresh в Qt; таблица AuthSession с хешем refresh, сроком, устройством, цепочкой ротации и отзывом. Ротация атомарна, повторное использование обнаруживается. Для критичных действий проверять действительность серверной сессии. Refresh/logout должны иметь согласованный сценарий после истечения access. Для Angular — access в памяти с восстановлением через защищённый refresh-cookie; cookie-сценарий требует явной защиты от CSRF/проверки origin, а не механического переноса всех JWT в cookie.

Критерий: logout, сброс пароля и блокировка пользователя имеют проверяемый эффект; два одновременных refresh не создают две действительные ветви. Продолжительный экзамен не обрывается из-за короткого TTL.

### S5. Защита входа и reverse proxy — P1

Добавить лимиты по учётной записи и источнику, ограниченное замедление, аудит неудачных входов и защиту от блокировки целой школы с общим IP. Для AI — квоты по сессии и ограничения размера/частоты отдельных endpoints, сохранив существующий bounded queue.

Nginx передаёт `X-Forwarded-Proto`, но `Program.cs` не подключает ForwardedHeaders. Настроить доверенные proxy/networks, не принимать эти заголовки от любого клиента. Это нужно для корректных scheme/IP, лимитов и перенаправлений. См. [Microsoft: reverse proxy](https://learn.microsoft.com/en-us/aspnet/core/host-and-deploy/proxy-load-balancer?view=aspnetcore-10.0).

Ввести HSTS после проверки сертификатов и доменов; CSP сначала Report-Only, затем enforced с учётом Angular, blob-видео и ресурсов landing. Не включать includeSubDomains/preload без проверки всех поддоменов. См. [OWASP HSTS](https://cheatsheetseries.owasp.org/cheatsheets/HTTP_Strict_Transport_Security_Cheat_Sheet.html).

### S7. Локальные данные и контейнеры — P2

Qt хранит evidence-токены в JSON с установкой прав владельца; сами записи и очередь остаются на диске. Для токенов использовать хранилище ОС (DPAPI/Credential Manager на Windows), определить срок хранения и удаление после подтверждённой доставки. Это снижает риск утечки с диска, но не делает клиент доверенным на контролируемом студентом ПК.

В Dockerfile Core/Inference нет явного перехода на непривилегированного пользователя. Явно задавать non-root, минимальные capabilities, no-new-privileges, квоты CPU/RAM/диска и writable volumes только для необходимых данных. Вынести средства сборки из runtime AI-образа. Ключи Data Protection защищать отдельно от резервной копии БД, иначе вместе они позволяют восстановить выданные пароли.

Подписывать Windows installer и проверять артефакты выпуска. Это отдельная защита доставки приложения; HTTPS не заменяет подпись файла.

## Архитектура каждого приложения

### Core: модульный монолит

Сейчас есть API/BLL/DAL, но бизнес-сценарии используют и generic repository/UoW, и прямой DbContext; API-контроллеры и службы содержат операции с БД/файлами. Такой набор сам по себе не ошибочен, но общие правила доступа и транзакций легко разнести по разным путям.

Выделить внутренние модули **Identity**, **Roster**, **Exams**, **Attempts**, **Evidence**, **Review**, **Reporting**. У каждого — явные сценарии, политики доступа и DTO. Контроллер принимает запрос, вызывает сценарий и отображает результат. EF можно оставить инфраструктурой; не добавлять repository поверх каждого простого запроса ради формальности.

Начать с Review и Evidence: единая машина состояний попытки, revision/optimistic concurrency для решений, атомарная проверка актуальности доказательств. Затем вынести экспорт/выдачу паролей в отдельные разрешённые сценарии. Для внешнего API — OpenAPI-контракт, единый ProblemDetails, correlation ID, пагинация и пределы выборок.

Файлы вынести за `IEvidenceStorage`, metadata хранить в БД. Сначала реализовать текущий local volume, затем S3-совместимое хранилище без изменения бизнес-кода. Файловая запись и PostgreSQL не одна транзакция: нужны pending/committed состояния, outbox и восстановление незавершённых операций. Миграции из `DbInitializer.Initialize()` перенести в контролируемый deployment job перед масштабированием реплик.

Проверка расширяемости: новый тип наблюдения не требует правки всех контроллеров; смена хранилища не меняет Review; конкурентные решения возвращают понятный конфликт, а не молча перезаписываются.

### Inference: HTTP-слой, pipeline и исполнители моделей

Хорошая база уже есть: адаптеры моделей, policy, reducer эпизодов, durable outbox, capacity gates и readiness. Эти механизмы сохранить.

Разделить маршрут на проверку запроса → авторизацию попытки → pipeline → фиксацию результата. Модель возвращает факты и качество; policy определяет наблюдения; окончательное дисциплинарное решение остаётся у преподавателя. Добавить единый тип Observation с версиями модели/политики, capture time и provenance.

Сейчас модели кешируются в процессе, ограничители локальны, SQLite хранит challenge/эпизоды/outbox. Простое увеличение Uvicorn workers или реплик не является безопасным масштабированием. Для нескольких узлов выбрать владельца сессии либо общее транзакционное состояние; отдельные worker-процессы для моделей с известными лимитами памяти и очередью. При переносе состояния сохранить идемпотентность eventId/revision и атомарность episode+outbox. Redis не использовать как единственное хранилище доказательств.

Переиспользовать HTTP client к Core через lifespan; в `require_active_session` сейчас создаётся новый AsyncClient на запрос. Оптимизировать проверку lease только с явно ограниченным временем устаревания и отзывом. Выносить модели в независимые сервисы только при измеренной необходимости разных ресурсов/масштаба.

### Angular monitor: единая логика попытки и доказательств

Feature-структура уже есть. Основное дублирование — загрузка/восстановление видео, шкала, labels событий и ручное управление асинхронным состоянием в Monitor и ViolationDetail.

Выделить `EvidencePlayer`, `ObservationQueue`, `ObservationReview`, `AttemptReview`; добавить facade/store на попытку с состояниями loading/ready/stale/error и ключом sessionId+eventId+revision. RxJS/signals достаточно, тяжёлая библиотека state management не обязательна. Общий механизм отмены запросов и сохранения черновиков снижает риск смешать события при навигации.

Генерировать API-типы/клиент из OpenAPI, проверять обратную совместимость в CI. Сервер остаётся источником приоритета, прав и допустимых переходов; UI показывает причины недоступности действий. Route guards нужны для UX, но не считаются защитой API. Для больших экзаменов сначала пагинация и инкрементальные обновления; SSE/SignalR добавлять после измерения polling, сохраняя восстановление состояния через REST.

### Qt: явные состояния и единая сетевая политика

Сейчас есть viewmodels, CoreApiClient, MlApiClient и AuthService, но часть REST-запросов находится непосредственно в ExamViewModel; разные QNetworkAccessManager имеют разные настройки и жизненный цикл.

Выделить `ServerConnectionPolicy`, `AuthSession`, `ExamSessionCoordinator`, `CapturePipeline`, `UploadQueue`, `LocalEvidenceStore`. QML только отображает состояние и передаёт намерения пользователя. Общий transport отвечает за origin/TLS, таймауты, ошибки, refresh и отмену; повторы команд допускаются только при определённой идемпотентности.

Зафиксировать состояния: подготовка → допуск → экзамен → отправка ответов → доставка материалов → завершено. Потеря сети и восстановление — отдельные переходы, а не разрозненные bool. Сохранить тихий интерфейс во время экзамена и технические сообщения, необходимые для продолжения. При любом рефакторинге проверить offline/restart, expiry токенов и смену аккаунта с недоставленными записями.

### Landing и web-site

Landing — статическая страница загрузки, web-site — Astro/MDX документация. Не добавлять им доступ к биометрии и школьным API. Общие правила и сведения о релизе публиковать из версионированного manifest, чтобы Qt, landing и документация не расходились.

Внешние шрифты landing можно заменить локальными для автономности и более простой CSP. Релизы отделить от HTML-сборки: version, checksum, подпись, канал dev/prod, проверка соответствия manifest. Для сайта оставить статическую публикацию, если серверные возможности не нужны; dev-сервер не публиковать как production.

### Инфраструктура и эксплуатация

Свести варианты Compose к одному base и явно выбранным dev/prod overlays: сейчас есть несколько близких конфигураций с разными mounts и опубликованными портами. Проверка production должна подтверждать, что снаружи доступны только нужные HTTPS/redirect endpoints, а DB/AI/internal API не опубликованы напрямую.

Добавить метрики: задержка AI, длина очереди, недоставленные события, свободный диск, частота 401/403/429, полнота записи, срок сертификата. Не писать JWT, пароли, signed URL и биометрические материалы в обычные логи. Для видео исключить query-параметры подписи из access log либо редактировать их. Backup проверять восстановлением БД, evidence, AI-state и необходимых ключей в изолированном окружении.

## Предлагаемый порядок работ

1. Обновить проверенные уязвимые зависимости; повторить audit/тесты. Ввести обязательный HTTPS в production Qt и проверку production-профиля.
2. Закрыть доступ преподавателя к неназначенным группам/паролям; ввести лимиты входа и корректную обработку доверенного proxy.
3. Разделить криптографические ключи, затем внедрить AuthSession и согласованный refresh/logout в Angular и Qt.
4. Выделить общую логику Evidence/Review на сервере и фронте; добавить версию решения, защиту конкурентных изменений, единые контракты ошибок.
5. Выделить storage/state interfaces, добавить эксплуатационные метрики; только затем измерять и реализовывать горизонтальное масштабирование.

Для каждого шага — небольшой мигрируемый контракт, отдельные тесты и возможность отката. Переписывание всей системы одновременно сделает регрессии допуска, экзамена и доставки доказательств труднее обнаруживаемыми.
